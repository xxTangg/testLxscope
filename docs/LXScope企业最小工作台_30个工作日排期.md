# LXScope 企业最小工作台：30 个工作日排期

## 1. 文档目的

本排期基于两部分输入制定：

1. 领导 Demo 和《设计决策与项目出发点总结.md》体现的产品意图；
2. 当前 `agentscope-2.0.7.post1` 代码已经具备的 Agent、MCP、RAG、Workspace、事件流和 Web 工作台能力。

本计划采用“减法”原则：首期不追求完整企业平台，而是先交付一条企业敢用的最小闭环：

> 一个明确任务 + 一组授权材料 + 一组受控 MCP/工具 + 一个可追踪的 Agent Run + 必要的人工确认 + 一个可验证的文件产物 + 完整审计与恢复入口。

## 2. 工期结论

### 2.1 日历工期

首期总工期：**30 个工作日，6 周**。

第 22 个工作日形成第一条可演示的端到端闭环；第 26 个工作日形成可供业务试用的版本；第 30 个工作日完成发布验收。

### 2.2 人员假设

| 角色 | 主责 | 预计投入 |
|---|---|---:|
| 技术负责人/架构 | 边界设计、技术决策、验收 | 12 人日 |
| 后端/平台工程师 | Task、Run、Policy、MCP、Artifact 后端 | 25 人日 |
| 前端工程师 | 任务创建、运行时间线、MCP 管理、产物页面 | 18 人日 |
| 运维/安全工程师 | 部署、隔离、密钥、故障演练、安全验收 | 15 人日 |
| 实习生 | 框架调研、测试、文档、隔离 PoC、回归脚本 | 14 人日 |
| **合计** |  | **约 84 人日** |

这里的 30 天是日历工期，不是 30 人日。若只有 1 名全职开发，工期应按约 84 人日重新换算，不应直接承诺 30 天交付。

## 3. 首期范围与明确不做项

### 3.1 首期必须交付

- 任务创建、任务状态和任务运行记录；
- `tenant_id/user_id/task_id/run_id/agent_id/session_id/workspace_id/artifact_id` 全链路标识；
- 模型、RAG、MCP、工具、人工确认的统一事件记录；
- MCP 注册、版本、健康状态、风险等级、启停和授权；
- 按租户、用户、Agent、任务的最小工具策略；
- 材料授权快照和引用来源；
- 暂停、恢复、取消、重试和失败原因；
- 文件产物生成、校验、归属、下载授权和版本信息；
- 至少一种强隔离 Workspace 的可验证 PoC；
- 一套端到端演示和回归测试。

### 3.2 首期明确不做

- 完整的企业组织管理后台；
- 完整 RBAC、计费、商业配额和应用市场；
- 任意 Shell、任意网络访问、任意脚本执行；
- 完整 BPMN 规范、并行网关、消息节点和定时器节点；
- 全量 Office 专业排版能力；
- 移动端、实时语音和所有第三方频道；
- 自动化的通用多 Agent 编排；
- 完整灾备体系和跨地域容灾。

注意：虽然完整多租户后台后置，但租户上下文、资源归属、跨租户拒绝和审计字段必须在第 1 天纳入设计，不能最后补。

## 4. 能力框架映射

| 排期阶段 | 主要对应能力框架 | 阶段结束后达到的程度 |
|---|---|---|
| 阶段 0：范围和边界 | 全部能力层、运行基础层 | 明确什么可以执行、什么必须拒绝，形成最小产品合同 |
| 阶段 1：可观测性底座 | 运行基础层、Agent 核心能力层、模型能力层 | 一次运行能够解释“谁在什么任务中调用了什么模型、材料、MCP 和工具” |
| 阶段 2：MCP 治理 | 生态接入层、运行基础层、用户与运营层 | MCP 从“能接入”变成“可登记、可授权、可停用、可审计” |
| 阶段 3：任务/Harness | 工作台层、Agent 核心能力层、知识与记忆层 | 从聊天升级为可暂停、可确认、可恢复的受控任务 |
| 阶段 4：确定性产物 | 工作台层、知识与记忆层、运行基础层 | 输出文件有来源、归属、版本、校验和下载控制 |
| 阶段 5：集成验收 | 全部能力层 | 形成一条可以向企业演示和试用的最小工作台闭环 |

## 5. 每日排期

负责人缩写：技术负责人 `TL`，后端 `BE`，前端 `FE`，运维/安全 `OPS`，实习生 `INT`。

### 阶段 0：定义最小边界（第 1—3 天）

| 天数 | 当日任务 | 主责 | 当日交付物 | 验收标准 |
|---:|---|---|---|---|
| D1 | 启动会；确认首期唯一业务场景，建议选“授权材料分析并生成报告”；把领导文档中的目标、原则和禁止项转成需求清单 | TL、BE、FE、OPS | 《首期范围与验收标准》 | 所有人对“首期做什么、不做什么”无歧义 |
| D2 | 盘点当前 AgentScope 代码能力：Agent、Session、Pipeline、MCP、Skill、RAG、Workspace、事件流、Token 统计、前端页面 | TL、INT | 《现有能力—目标能力矩阵》 | 每项能力标记为：可直接复用、需产品封装、仅有接口、暂缺 |
| D3 | 定义核心对象和责任边界：Tenant、User、Task、Run、Material、Policy、Workspace、Artifact、Approval、AuditEvent；确认高风险工具默认关闭 | TL、BE、OPS | 数据对象草图、风险工具清单、首期架构图 | 高风险能力没有默认放行项；所有对象都有归属字段 |

**阶段门 G0：** 不通过 G0，不进入开发。必须先回答“任务是什么、材料是什么、允许调用什么、结果交付给谁、失败如何处理”。

| 天数 | 当日任务 | 主责 | 当日交付物 | 验收标准 |
|---:|---|---|---|---|
| D4 | 设计统一事件模型和关联 ID；规定事件类型：Task、Run、Model、RAG、MCP、Tool、Human、Artifact、Error | BE、TL | `AuditEvent`/运行事件规范 | 任意事件都能关联到租户、任务、运行和操作者 |
| D5 | 设计 Task、Run、Artifact 的最小数据结构和状态机；确定持久化策略 | BE | 数据库迁移/模型草案 | 可表达创建、运行、暂停、失败、重试、完成、取消 |
| D6 | 实习生调研 OpenTelemetry、现有 AgentScope tracing、日志结构和指标方案；同时调研 Keycloak/OpenFGA/OPA 是否需要接入 | INT、OPS、TL | 技术选型备忘录 | 给出“首期采用/暂不采用”的明确结论，不只罗列产品 |
| D7 | 建立本地开发、测试、演示三套配置；补齐 Redis/数据库/消息总线启动检查 | OPS、BE | 环境配置和启动检查脚本 | 新环境可以按文档启动，错误配置能在启动阶段暴露 |
| D8 | 接入任务级 Trace 和事件采集；覆盖 Session、Agent、Model 调用 | BE | 后端事件中间件初版 | 一次模型调用能查到完整任务和运行上下文 |
| D9 | 接入 RAG、MCP、Tool、Workspace、Human Confirmation 事件 | BE、INT | 事件采集扩展、测试数据 | 事件时间顺序正确，失败事件不会被吞掉 |
| D10 | 提供运行时间线查询 API 和基础指标 API：耗时、Token、错误、重试、MCP 调用次数 | BE、FE | `/tasks/{id}/runs` 等查询接口 | 能按任务查看从开始到结束的运行轨迹 |

**阶段门 G1：** 给定一个测试任务，可以回答“谁、何时、调用了什么、用了什么材料、耗时多少、哪里失败”。否则不得进入 MCP 治理开发。

### 阶段 2：MCP 治理和工具边界（第 11—16 天）

| 天数 | 当日任务 | 主责 | 当日交付物 | 验收标准 |
|---:|---|---|---|---|
| D11 | 设计 MCP Catalog：名称、来源、版本、能力、风险等级、健康状态、负责人、适用租户 | BE、INT | MCP 注册表模型和字段说明 | 每个 MCP 都有明确来源、版本和责任人 |
| D12 | 实现 MCP 注册、更新、版本锁定、健康检查和启停 API | BE、OPS | MCP 管理 API | 未登记或未启用的 MCP 不能被任务调用 |
| D13 | 实现最小 Policy：租户/用户/Agent/Task 四级授权；默认拒绝，逐级放行 | BE、TL | Policy 接口和策略测试 | 未授权 MCP、工具、资源调用全部拒绝并留下审计事件 |
| D14 | 实习生完成 Docker/OpenSandbox/Daytona 等隔离方案 PoC；OPS 明确文件、网络、进程和资源边界 | INT、OPS | 隔离对比表、PoC 记录、威胁模型 | 至少选定一种首期可用的强隔离运行方式 |

| 天数 | 当日任务 | 主责 | 当日交付物 | 验收标准 |
|---:|---|---|---|---|
| D17 | 实现 Task API 和状态机：Draft、PendingApproval、Running、WaitingHuman、Paused、Failed、Retrying、Completed、Cancelled | BE | Task 服务和状态迁移测试 | 非法状态迁移会被拒绝；每次迁移有事件 |

| D24 | 增加格式、结构和必填内容校验；记录生成模型、模板、输入材料和任务版本 | BE、INT | Artifact 校验器、来源元数据 | 校验失败时任务状态明确，不伪装成成功 |

| 天数 | 当日任务 | 主责 | 当日交付物 | 验收标准 |
|---:|---|---|---|---|
| D27 | 执行隔离测试：跨用户、跨租户、跨任务工作区访问；未授权文件、网络、命令和 MCP 调用 | OPS、INT、BE | 安全测试报告 | 所有越权用例默认失败；失败有审计记录 |
| D28 | 执行故障演练：模型超时、MCP 不可用、网络异常、重复提交、进程重启、任务恢复 | OPS、BE | 故障演练记录和恢复 Runbook | 系统不虚报成功；可重试、暂停或恢复的任务行为明确 |
| D29 | 业务试用和演示；收集“看不懂、不能控制、不能恢复、结果不可信”的问题 | TL、FE、INT | 试用问题清单、演示脚本、用户手册 | 非研发人员能完成一次完整任务并解释结果来源 |
| D30 | 发布评审；确认首期能力边界；冻结版本；形成下一阶段 backlog | 全员 | 发布验收单、版本说明、后续路线图 | 通过 G5 才能称为“企业最小工作台”试点版 |

**阶段门 G5：** 至少通过以下五项硬性验收：

1. 未授权 MCP、工具、材料、产物访问全部拒绝；
2. 每个任务有完整运行时间线和审计记录；
3. 任务可以人工暂停、恢复、取消和重试；
4. 产物有来源、版本、归属和下载授权；
5. 发生异常时系统明确展示失败，不伪造“正在处理”或“已完成”。

## 6. 实习生的具体安排

实习生适合从研究、验证和自动化测试切入，但不应独立承担企业安全边界的最终决策。

### 实习生任务表

| 日期 | 研究/开发任务 | 产出 |
|---|---|---|
| D2 | 对照当前代码盘点能力 | 能力矩阵初稿 |
| D6 | 调研 OpenTelemetry、Keycloak、OpenFGA、OPA 与当前代码的接入成本 | 选型备忘录 |
| D9 | 补齐 Agent、RAG、MCP、Tool、Workspace 事件测试数据 | 事件回归样例 |
| D11 | 设计 MCP Catalog 字段和风险分类 | MCP 登记模板 |
| D14 | 对比 Docker、OpenSandbox、Daytona 等隔离方式 | 隔离 PoC 和对比结论 |
| D16 | 编写 MCP 未授权、停用、版本不匹配测试 | MCP 治理测试集 |
| D19 | 验证材料来源和版本追踪 | SourceRef 测试样例 |
| D24 | 编写产物格式、归属和来源校验测试 | Artifact 测试集 |
| D27 | 执行跨用户、跨租户、跨工作区越权测试 | 安全测试报告 |
| D29 | 按业务用户视角执行试用并记录问题 | 可理解性问题清单 |

实习生阶段性研究目标不是“研究完所有框架”，而是回答三个可执行问题：

1. 哪一种隔离方式能在当前环境中真正跑起来；
2. 哪些能力可以直接复用 AgentScope，哪些必须由 LXScope 自己补；
3. 哪些安全和治理用例可以自动化验证。

## 7. 首期架构落点

```text
身份/租户上下文
        ↓
Policy / MCP 治理 / 材料授权
        ↓
Task / Run / Harness
        ↓
Agent / Model / RAG / MCP / Tool / Sandbox
        ↓
人工确认 / Artifact / Audit / Recovery
```

当前 AgentScope 的 `Session`、`Agent`、`Workspace` 和 `Message` 可以继续作为底层实现，但 LXScope 必须在上面增加任务级对象和责任边界，不能继续把 Session 直接当成企业任务。

## 8. 需要领导确认的三个决策

### 决策一：首期业务场景

建议只选一个能形成文件产物的场景，例如：

> 企业内部资料检索、分析并生成带来源的调研报告。

它能够一次性验证材料授权、RAG、MCP、Agent 推理、人工确认、文件生成、审计和恢复。

### 决策二：首期隔离等级

建议首期禁止任意宿主机工具；需要代码、Shell 或网络访问时，必须进入 Docker/OpenSandbox 等独立运行空间。若强隔离 PoC 未通过，首期只开放无副作用的白名单工具。

### 决策三：首期企业化范围

建议首期做“租户上下文 + 资源归属 + 默认拒绝 + 审计”，暂不做完整的组织管理、计费和应用市场。这样既不会把项目拖入登录注册和后台管理，也不会留下无法补救的数据隔离漏洞。

## 9. 排期后的最终产品判断

30 个工作日后，项目可以合理宣称：

> LXScope 已具备企业最小 AI 任务工作台能力：任务可定义、材料有授权、MCP 可治理、执行可观测、过程可干预、结果可追溯、异常可恢复。

但不能宣称已经完成：

- 完整企业级多租户平台；
- 完整 RBAC 和计费体系；
- 任意代码执行的生产级强隔离；
- 通用 BPMN 平台；
- 完整灾备和企业级运维平台。

这些应作为第二阶段路线，而不是混入首期最小工作台。
